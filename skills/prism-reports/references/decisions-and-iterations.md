# Decision pages and iterations

## Decision pages

Whenever the user must pick, approve or answer anything, render `templates/decision-page.html`, even for one yes/no and even when they did not ask for HTML. The user answers by clicking, never by typing in the terminal what the page could collect.

- **Header**: the main question as h1 ("Which X should we ship?"), the recommendation in one sentence with the reason, a meta line with the round number, date and what happens after the picks.
- **One thing** (the CTA block): `p.one` says how many questions to answer and to send them ("Answer 2 questions, then <span class="verb">Send results</span> (top right)."; the script renames `.verb` to Copy results when the page is opened as a file); the questions follow as `ol.next`, each linked to its section, with "X recommended" as the muted words.
- **Questions**: every `.opts[data-q="<question>"]` is one question; the page can hold several (pick a design, approve a plan, choose a name). Add `data-multi` when several picks are allowed (which screens to keep). **Approving a set item by item** (a still per character, a background per scene, a voice per line) is one question with **row picks**, never "Yes, all my picks" vs "Change some": add `data-rows` and put one `.row[data-row="Geek"]` per item, each holding small tiles (`<article class="opt" data-key="1"><img src="..." alt="..."><div class="opt-h"><b>Try 1</b><span class="chip good">Recommended</span></div><button class="pick" type="button">Pick</button></article>`, no link on the image: a tap anywhere picks). One pick per row; the script adds the row name, a Redo tile, a note per row that shows once the row has a pick (Redo focuses it; Add note opens it early), and a bar with the count and **Pick all recommended**. Results read `Geek: Try 1; Athlete: Redo (note: ...)`. Yes/no and approvals use the same cards without previews (`data-key="Yes" data-name="ship Friday"`). The template script adds a note box under each question (it grows as you type; paste or drop images on any note, several at a time, and they show as thumbnails under it; Send results uploads them, the answer server saves them to a temp folder, `$TMPDIR/prism-notes/`, and the answers read `[image: /full/path.png]` for the agent to open; Copy results leaves them out), a **Select all / Deselect all** bar with the count above every `data-multi` question, and a **Next question** button under each note that jumps to the next question. The last question has no Next button: under it comes the general note, **Anything else? (optional)**, skippable, then the button that sends (or copies) the results. **Cmd+Enter** (Ctrl+Enter) walks it from the keyboard: next question (focus on its first Pick), then the general note, then a confirmation that lists every answer; Cmd+Enter or Enter there sends, Esc goes back. The Next buttons show the shortcut. On screens 1180px and wider a **question sidebar** (`nav.wiz`) is docked down the left edge from the start, the page beside it: every question as a step with its answer, the one on screen in bold, click to jump. **Focus**: once the reader reaches the questions, every question but the one on screen dims (no blur), and the cards not picked in an answered question dim. A card whose chip reads `Recommended` gets a green frame and a solid chip, and the results button is green (tinted until every question is answered, then solid, with a send icon when served). Nothing to write for any of these. The button fills once its question has an answer.
- **Options** (`article.opt[data-key][data-name]` inside `.opts`): 2-4 side by side (one column on phones). Design options have a letter and a short name, a one-line description, a preview (the option's own mock, screenshot or video, inside its card's `.preview`: never in a gallery above or beside the cards, so what you pick and its Pick button stay together; `check-report.mjs` fails a figure captioned with an option's name outside its card; a live-HTML mock drawn for a fixed width gets `data-w="460"` and is scaled to fit the card like a thumbnail, never clipped; every image in a card gets a small expand button that opens it full size, nothing to write), 1-3 pros and cons (`.pc` with `li` / `li.con`), and a Pick button. When there is a recommendation, that option carries a `Recommended` chip. Pros and cons only when known; never invent them to fill a card.
- **Send results** (`button.copy-all`, last item in `nav.toc`): pinned right in the sticky top bar, shows `answered/total`. Served by `scripts/collect-answers.py`, one click posts the answers to the server; the server prints them and exits, and the tab stays ("Sent, next round loads here") and reloads itself when the next round lands. A **Copy** button sits right before it, for a copy of the same block. Opened as a file it reads **Copy results** and copies one block to paste back in the chat. Answers and notes are remembered per page. After a copy, a **Close tab** button springs in right next to it in the top bar (Motion from the pinned CDN, loaded on the first pick; plain when offline or with reduced motion): it closes the tab when the browser allows it (a page opened from the terminal is allowed) and otherwise names the shortcut. Keep the script as it is.

  ```
  Answers from "<h1>" (/abs/path/page.html)
  1. <question>: B (<name>). Note: <note>
  2. <question>: Yes (ship Friday)
  3. <question>: no answer
  General note: <note>
  ```
- **Previews show the real thing**: the actual page section with each variant's CSS applied, a screenshot, or a mockup in the product's own style. Same content in every option so only the variable differs.
- **Compare**: a short sortable table of only the criteria that decide it, with SVG icons.
- Hand it over live: run `python3 <plugin>/scripts/collect-answers.py <page.html>` as a background command (it opens the page in the browser and prints its `http://127.0.0.1:<port>/` URL on stderr; it waits up to 4 hours, `--timeout` to change). The port is fixed per page and the open tab polls it, so a rerun for the next round reloads that tab instead of opening a new one, and a server already holding the port hands over to the new one. Hand over that URL with the page's index and hub links, and say: click your answers, then Send results. When the command exits, its stdout is the block above, from the user's own clicks: apply every answer, then update the page: the next round on top, or a "Decided" state. Without background commands, hand over the file link and ask for Copy results pasted back.

## One topic, one page: rounds are tabs

A follow-up on the same topic is a new round on the same page, never a new file. A new topic (the chat moved from keywords to a domain pick) is a new page, never a tab: link the two pages both ways, a link in each meta line.

- **One round**: a plain page, no tabs, plain ids.
- **From round 2 on**, each round is a tab, newest first. Markup, right after the back link:

  ```html
  <nav class="rounds"><a href="#round-3">Round 3</a><a href="#round-2">Round 2</a><a href="#round-1">Round 1</a></nav>
  <div class="round" id="round-3"> header, .cta, nav.toc, sections </div>
  <div class="round" id="round-2"> ... </div>
  ```

  Each `div.round` is a whole page: its own h1, lede, One thing, `nav.toc` and sections; its meta line or first section says what changed since the previous round (`.round-meta`). Every id inside starts with the round id (`round-2-compare`, `round-2-opt-B`) so rounds never clash; when round 2 lands, wrap round 1 in its `div.round` and prefix its ids. The newest round comes first and shows by default (its tab reads "latest"). Tab labels stay short: "Round 3", or "Round 3: finalists".
- **Only the newest round can be picked.** Questions (`.opts[data-q]`) and the Send results button sit only in the first round. When a new round lands, the previous one becomes a record: its answered questions turn into Decided cards (no `data-q`, no Pick buttons, the pick in the user's words) and its One thing reads the decision. Earlier options keep their previews (screenshots are fine).
- **Links**: `page.html#round-2` opens that round, and so does any id inside it (`page.html#round-2-compare`). The index lists each round under the page's row. The `<title>` names the topic.
- **Checks**: `check-report.mjs` wants one One thing per round, one tab link per round, no questions outside the first round, and no tabs for a single round.
- **Template**: the tabs and the reload are in every template; `decision-page.html` shows two rounds. A report-only page that gets its first question takes that template's style and script blocks.
- **One browser tab**: serve the page once with `collect-answers.py`. While the server runs, a new round only rewrites the file and the tab reloads itself onto the newest round, at the top. After it exits (answers sent), rerun it for the next round: same port, same browser tab.
- **Versions** of a report updated after feedback, and decided pages, follow the same rule: the decided page shows what shipped as the newest round. The index sorts pages oldest first; inside a page, newest first.
- **Older pages** may still list rounds in `nav.toc` (`.latest`) with earlier rounds in `<details>` under "Earlier rounds". `fix-report` turns them into tabs.
